## О проекте

Данный проект представляет собой пример моего кода, основная цель которого, заключается имено в том, чтобы продемонстрировать архитектуру игры.

Проект реализует MVP типичного игрового сценария для мобильных игр — ограниченное по времени событие (Limited-Time Event). В рамках события реализован внутриигровой магазин с тремя предложениями, доступными для покупки. Конфигурация события полностью настраивается через JSON-файл.

Реализован только необходимый минимальный UI: отображение ресурсов игрока (HUD), кнопка открытия магазина и сам магазин. Также реализованы Save-Load система и инструмент для удаления прогресса игрока непосредственно из Unity Editor.

Более подробное описание архитектуры приведено ниже, в разделе Архитектура.

### 1. Базовые принципы и паттерны

[_Вернуться к содержанию раздела Архитекутра_](#архитектура)

Прежде чем переходить к описанию отдельных подсистем, важно обозначить инженерные принципы, которыми я руководствовался при разработке проекта. Именно они объясняют, **почему архитектура построена именно таким образом**.

**Как принципы SOLID практически применены в проекте:**

* **Single Responsibility Principle (SRP)** — каждый класс имеет только одну причину для изменения. Например, `SaveLoadService` отвечает исключительно за сохранение и загрузку данных и ничего не знает о механике покупок. `TripleOfferEvent` управляет исключительно жизненным циклом игрового события и не содержит логики работы таймера. Именно поэтому проект состоит из множества небольших специализированных сервисов, а не нескольких крупных классов.
* **Open/Closed Principle (OCP)** — новая функциональность (например, новый тип игрового события, новое предложение магазина или другой способ хранения данных) добавляется путём создания новых реализаций существующих интерфейсов, без изменения уже работающего кода.
* **Liskov Substitution Principle (LSP)** — любая реализация `IService`, `IState`, `ISaveLoadService` и других интерфейсов может быть заменена другой без изменения поведения системы, поскольку остальные компоненты зависят только от контракта, а не от конкретной реализации.
* **Interface Segregation Principle (ISP)** — каждый интерфейс предоставляет только тот функционал, который действительно необходим его потребителям. Например, `ISaveLoadService` не содержит методов, относящихся к работе `IAPService`.
* **Dependency Inversion Principle (DIP)** — высокоуровневая логика (Game State Machine, Presenters, игровые события) зависит исключительно от абстракций (интерфейсов, наследуемых от `IService`), тогда как конкретные реализации передаются через Dependency Injection и никогда не создаются напрямую внутри классов. Именно этот принцип является фундаментом всей архитектуры Dependency Injection, описанной далее.

**Помимо SOLID, в проекте последовательно применялись следующие паттерны и правила:**

* **Именование как часть документации**. Названия классов отражают их ответственность, а не особенности реализации (ISaveLoadService, а не JsonFileManager). Благодаря этому название остаётся актуальным даже при полной замене внутренней реализации, что особенно важно для обеспечения расширяемости проекта.
* **Композиция вместо наследования**. Сервисы формируются посредством внедрения зависимостей через конструкторы, а не за счёт построения сложных цепочек наследования. Наследование используется только там, где оно действительно оправдано — в виде небольших интерфейсов (IState, IService), что позволяет избежать проблемы «хрупкого базового класса» (Fragile Base Class Problem).
* **Dependency Inversion как архитектурный принцип**. Все зависимости между сервисами представлены исключительно интерфейсами. Ни один сервис не обращается напрямую к конкретной реализации другого сервиса. Именно это позволяет контейнеру Dependency Injection (Zenject) эффективно управлять зависимостями.
* **Защищённое программирование**. Перед выполнением логики методы всегда проверяют входные данные и необходимые предусловия. Например, методы OfferDataService.IsConfigValid(), IsOffersListValid() и IsEventValid() внутри TripleOfferEvent. Некорректные состояния обнаруживаются максимально рано и обрабатываются явно (возвращается пустая коллекция или false), не допуская распространения ошибок, которые впоследствии могли бы привести к исключениям NullReferenceException. 
* **"Fail Fast" с корректной обработкой ошибок контента**. Ошибки загрузки конфигураций выявляются непосредственно в месте возникновения и сразу фиксируются через Debug.LogError, а не скрываются и не проявляются спустя несколько уровней вызовов. При этом отсутствие или повреждение конфигурации события не приводит к аварийному завершению работы игры — система корректно деградирует до состояния «событие недоступно», поскольку ошибки контентных данных не должны приводить к остановке игрового приложения. 
* **Сначала интерфейс, а затем реализация**. Каждый сервис сначала проектируется как контракт (ISaveLoadService), и только после этого создаётся его реализация (SaveLoadService). Такой подход заставляет заранее определить публичный API сервиса и не допустить попадания деталей реализации во внешний интерфейс. 
* **Низкая связность между модулями и высокая связность внутри модуля**. Каждый класс сфокусирован на решении одной конкретной задачи (например, OfferDataService отвечает исключительно за работу с данными предложений), а взаимодействие между компонентами происходит через минимально необходимый набор интерфейсов. Именно сочетание высокой внутренней связности и слабой связанности между компонентами делает систему легко заменяемой, расширяемой и удобной для тестирования.

Все перечисленные принципы являются основой архитектуры данного проекта. Именно они определили структуру сборок, использование Dependency Injection, сервисную архитектуру, Game State Machine и MVP. Каждый последующий раздел демонстрирует практическое применение этих инженерных принципов при решении конкретных архитектурных задач.

### 2. Assembly Definition структура

[_Вернуться к содержанию раздела Архитекутра_](#архитектура)

Проект разделён на отдельные Assembly Definition (`.asmdef`): **Core**, **Services**, **Infrastructure**, **UI Logic**, **Events**, **Editor**.

![img_1.png](img_1.png)

*Граф зависимостей сборок также приведён на UML-диаграмме, его можно посмотреть на той же схеме [[ссылка на карту Miro](https://miro.com/app/board/uXjVHBx50zk=/)].*

**Почему вообще было принято решение разделить проект на отдельные сборки?**

Если весь проект находится в одной стандартной сборке, Unity перекомпилирует весь код при любом, даже самом незначительном изменении скрипта. По мере роста проекта это становится одним из основных источников потери времени при разработке. Использование Assembly Definition позволяет Unity перекомпилировать только изменённую сборку и те сборки, которые от неё зависят, тогда как остальные остаются нетронутыми.

Разделение на сборки даёт следующие преимущества:

* **Сокращение времени компиляции** — изменение скрипта в **UI Logic** не приводит к перекомпиляции **Core** или **Services**.
* **Явно определённые и принудительно контролируемые зависимости** — сборка может использовать типы только из тех сборок, которые явно указаны в её `.asmdef`. Благодаря этому архитектурные границы перестают быть лишь соглашением между разработчиками и начинают контролироваться компилятором. Например, если **Services** попытается обратиться к коду из **UI Logic**, проект просто не скомпилируется.
* **Предотвращение циклических зависимостей** — система сборок Unity полностью запрещает циклические ссылки между `Assembly Definition`. Это заставляет поддерживать ациклический граф зависимостей и позволяет выявлять архитектурные ошибки (например, когда низкоуровневый сервис неожиданно начинает зависеть от высокоуровневого слоя) ещё на этапе компиляции.
* **Модульность** — каждая сборка представляет собой отдельный логический слой приложения (контракты данных, сервисы, инфраструктура, слой представления, логика игровых событий и т.д.), благодаря чему становится значительно проще понимать структуру проекта и взаимосвязи между его компонентами.
* **Масштабируемость** — по мере развития проекта новая функциональность добавляется в соответствующую ей сборку, а не накапливается в одном общем пространстве кода.

**Почему сборка `Editor` выделена отдельно?**

Сборка **Editor** намеренно полностью изолирована: она не зависит ни от одной другой сборки проекта, и при этом ни одна сборка не зависит от неё.

Причина заключается в том, что код, предназначенный исключительно для редактора Unity (кастомные инспекторы, инструменты валидации ассетов, вспомогательные утилиты для разработки и т.п.), использует API пространства имён **UnityEditor**, которое отсутствует в финальной сборке игры.

Если такой код не изолировать в отдельную Assembly Definition, предназначенную только для платформы **Editor**, он либо не позволит собрать проект, либо, что ещё хуже, может случайно попасть в релизную сборку. Отдельная сборка гарантирует, что редакторские инструменты никогда не окажутся в Runtime-коде, а Runtime-код, в свою очередь, не сможет случайно начать зависеть от функциональности редактора.

### 3. Dependency Injection

[_Вернуться к содержанию раздела Архитекутра_](#архитектура)

Dependency Injection является ключевым архитектурным решением данного проекта. Именно вокруг него построена вся остальная архитектура, поэтому этот раздел требует наиболее подробного объяснения.

#### 3.1 Почему вообще выбран паттерн Dependency Injection?

В Unity наиболее распространёнными альтернативами Dependency Injection являются **Singleton** и **Service Locator**. Оба варианта были рассмотрены, однако сознательно не использовались.

**Почему не "синглтон"?**

Использование Singleton (например, `SaveLoadService.Instance`) создаёт глобально доступный экземпляр объекта, к которому может обратиться любой класс из любой части проекта. Такой подход имеет несколько серьёзных недостатков:

* **Скрытые зависимости** — если внутри класса используется `IAPService.Instance`, это никак не отражено в его публичном API. Чтобы понять, от чего зависит класс, необходимо изучать его внутреннюю реализацию.
* **Сложности при тестировании** — невозможно подменить зависимость тестовой реализацией (mock/fake), поскольку класс жёстко привязан к статическому экземпляру.
* **Неявное глобальное состояние и проблемы жизненного цикла** — появляется необходимость неявно контролировать, кто создаёт Singleton, когда он инициализируется и в каком порядке происходит его жизненный цикл.
* **Высокая связность** — доступ к `Instance` из любого места проекта постепенно разрушает архитектурные границы между слоями приложения и приводит к сильной связанности компонентов.

**Почему не Service Locator?**

Использование **Service Locator** (например, `ServiceLocator.Get<ISaveLoadService>()`) устраняет проблему единственного глобального экземпляра и позволяет получать зависимости через интерфейсы, что уже лучше по сравнению с Singleton.

Однако данный подход по-прежнему имеет ряд существенных недостатков:

* **Зависимости остаются скрытыми** — они находятся внутри методов, а не объявляются через конструктор. Чтобы понять реальные зависимости класса, всё равно приходится изучать его код.
* **Ошибки обнаруживаются только во время выполнения** — если сервис не зарегистрирован, `Get<T>()` вернёт `null` или выбросит исключение уже во время работы приложения, а не на этапе конфигурации системы.
* **Публичный API класса не отражает его реальные зависимости** — это значительно усложняет код-ревью, сопровождение и модульное тестирование.

#### 3.2 Почему именно Zenject?

Важно уточнить, что выбор **Zenject** не означает утверждение о том, что это лучший DI-контейнер для Unity.

Zenject был выбран потому, что это один из наиболее зрелых и широко используемых DI-фреймворков в экосистеме Unity. Он предоставляет богатый набор возможностей, проверенных большим количеством коммерческих проектов: **Installers**, **Factories**, **Memory Pools**, **Signals**, а также интерфейсы жизненного цикла, такие как `IInitializable`. Помимо этого, Zenject обладает обширной документацией и большим профессиональным сообществом.

**Почему не самописный DI контейнер?**

Создание собственного DI-контейнера является хорошим учебным упражнением, однако в реальном проекте это означает повторную реализацию уже давно решённых задач: управление временем жизни объектов, обнаружение циклических зависимостей, генерация фабрик, проверка корректности регистраций и многих других механизмов.

Использование готового зрелого решения позволяет сосредоточиться на разработке игрового функционала, а не на создании инфраструктуры. **Кроме того, любой разработчик**, изучающий проект, уже знаком с данным инструментом либо может быстро разобраться благодаря существующей документации и накопленному сообществом опыту.

**Почему не VContainer?**

Выбор Zenject не означает, что он объективно лучше **VContainer**.

VContainer — современный, производительный и значительно более лёгкий DI-контейнер. Он не использует рефлексию во время разрешения зависимостей, создаёт меньше аллокаций и отлично подходит для проектов, где производительность является критически важной.

Но всё же выбор пал именно на Zenject в связи с его большей популярьностью. Фактически разница в применении в коде между VContainer и Zenject не велика.

### 4. Entry Point

[_Вернуться к содержанию раздела Архитекутра_](#архитектура)

В проекте есть единая, четко контролируемая точка входа: класс `GameBootstrapper`, который реализует Zenject интерфейс `IInitializable`.


**Зачем применяется паттерн "Единая точка входа"?**

В игре есть множество систем, которые должны запускаться в определенном, предсказуемом порядке — сервисы должны существовать до того, как их сможет использовать конечный автомат, сохраненный прогресс должен загружаться до того, как запустится первое игровое состояние, и так далее. Без единой определенной точки входа логика запуска имеет тенденцию разбрасываться по множеству вызовов `MonoBehaviour.Awake()/Start()`, относительный порядок которых зависит от настроек порядка выполнения скриптов Unity — это печально известный, хрупкий и легко ломающийся механизм, особенно по мере роста проекта. Единая точка входа делает запуск игры явным и контролируемым разработчиком, а не Unity движком.

**Почему `IInitializable`, а не `Awake/Start`?**

`IInitializable` — это интерфейс жизненного цикла Zenject, который гарантирует, что метод `Initialize()` будет вызван только после того, как контейнер завершит разрешение и внедрение всех биндингов. Это устраняет целую категорию ошибок, когда `MonoBehaviour.Awake()` пытается использовать внедренную зависимость до того, как Zenject фактически успел ее внедрить. Это привязывает время запуска к жизненному циклу DI-контейнера, а не к жизненному циклу компонентов Unity, что является именно той гарантией, которая нужна загрузчику: _"выполнить это только после того, как все необходимое будет готово"_.

**Почему `GameBootstrapper` занимается только запуском и ничем больше?**

Это прямое применение Single Responsibility к самому важному классу в проекте. Единственная задача `GameBootstrapper` — инициировать самый первый переход (как правило, в начальное состояние Game State Machine, описанное ниже) — он не содержит игровой логики, UI-логики или логики сервисов. Если поведение при запуске нужно изменить (например, добавить заставку, добавить получение удаленной конфигурации перед запуском всего остального), это изменение происходит в одном маленьком, хорошо понятном классе, а не оказывается погребенным внутри MonoBehaviour, который также отвечает за полдюжины других вещей. Это делает точку входа понятной — любой новый человек в проекте может открыть `GameBootstrapper`, прочитать несколько строк и понять, что происходит в первую очередь.

### 5. Модульная архитектура

[_Вернуться к содержанию раздела Архитекутра_](#архитектура)

Логика проекта разложена на независимые сервисы, а не на небольшое количество больших классов-менеджеров. Примеры сервисов в проекте: `SaveLoadService`, `OfferDataService`, `IAPService`, `AddressableAssetProvider` и другие.

**Зачем вообще разбивать архитектуру на сервисы?**

Каждый сервис представляет одну целостную возможность приложения — сохранение, данные о предложениях/конфигурации, покупки, загрузка ресурсов — и ничего больше. Это прямое, практическое применение Single Responsibility Principle на уровне системы (а не только на уровне класса): вместо одного `GameManager`, который знает обо всем сразу — о сохранении, покупках, загрузке ресурсов и настройке событий — каждая из этих областей живет в своем собственном сервисе с собственным узким интерфейсом.

**Почему сервисы взаимодействуют через интерфейсы (`IAPService`, `ISaveLoadService`, `IOfferDataService`), а не через конкретные классы?**

Это Dependency Inversion Principle на практике: клиент, такой как `TripleOfferEvent`, зависит от абстракции `ISaveLoadService`, а не от конкретного класса `SaveLoadService`. Практическая выгода именно в том, что описано далее в обсуждении IAP — конкретную реализацию за интерфейсом можно заменить, не затрагивая ни одного из ее клиентов, потому что клиенты изначально не были связаны с реализацией.

**Принципы SOLID, наиболее явно проявляющиеся на этом уровне:**

* **Single Responsibility** — один сервис, одна возможность.
* **Dependency Inversion** — клиенты получают сервисы через интерфейсы, никогда через конкретный тип.
* **Open/Closed** — новые сервисы (или новые реализации существующих интерфейсов сервисов) расширяют систему без изменения классов, которым они нужны.
* **Interface Segregation** — каждый интерфейс сервиса предоставляет только операции, относящиеся к его собственной возможности, поэтому потребители никогда не вынуждены зависеть от методов, которые они не используют.

### 6. Game State Machine

[_Вернуться к содержанию раздела Архитекутра_](#архитектура)

Жизненный цикл приложения управляется конечным автоматом (FSM), или она же **Game State Machine** - машина состояний, а не одним монолитным менеджером.

#### 6.1 Для чего применён паттерн State Machine?

Жизненный цикл игры естественным образом проходит через дискретные фазы — загрузка прогресса, загрузка уровня, работа основного хаба — и у каждой фазы есть своя собственные настройки, поведение и условия выхода. Управление этми состояними явно в виде State машины, а не в виде клубка булевых флагов и if-проверок внутри одного большого класса, дает несколько конкретных преимуществ:

* **Явные контролируемые переходы**. Переход из одной фазы в другую — это преднамеренное, отслеживаемое действие (`Enter()/Exit()` у состояния), а не неявный побочный эффект от переключения какого-то флага где-то в большом классе.
* **Каждое состояние самодостаточно**. Состояние знает, как настроить себя и как очистить себя, и никому за пределами стейт-машины не нужно знать внутренние детали того, как работает конкретная фаза.
* **Нет "1000-строчного `GameManager`**. Это большое практическое преимущество такого подхода. Вместо того чтобы один класс накапливал в себе логику загрузки, логику перехода между уровнями и логику хаба — становясь все сложнее для безопасного изменения по мере роста — жизненный цикл приложения разбит на маленькие, независимые, одноцелевые классы. Это именно та декомпозиция, которая становится критически важной для долгосрочного здоровья кодовой базы по мере масштабирования проекта за пределы небольшого демо.
* **Каждое состояние имеет ровно одну фазу ответственности**, что является применением Single Responsibility Principle к управлению жизненным циклом приложения, а не к внутренним методам отдельного класса.

#### 6.2 Конкретные состояние, которые есть в проекте

`LoadProgressState`

Загружает сохраненный прогресс игрока из `SaveLoadService` и предварительно загружает Addressable-ресурсы ("Прогревает"), которые нужны на ранних этапах работы приложения, до того, как они реально понадобятся. Выполнение этих предварительных загрузок здесь — а не ленивая загрузка позже — сокращает видимое время загрузки в точках, находящихся дальше по ходу игры, где фризы были бы заметны для игрока (например, прямо в момент появления хаба).

`LoadLevelState`

Обрабатывает фактическую загрузку уровня/сцены и визуальное представление этой загрузки — т.е. `LoadingCurtain` или экран перехода, который скрывает от игрока процесс загрузки сцены.

**Почему `LoadProgressState` и `LoadLevelState` — отдельные состояния, а не одно комбинированное состояние "загрузки"?**

Это снова Single Responsibility: эти два состояния выполняют действительно разную работу. `LoadProgressState` занимается данными — получением сохраненных данных и прогревом кэша ресурсов — в то время как `LoadLevelState` занимается переходом между сценами и визуальными элементами загрузки, видимыми игроку. Разделение означает:

* Каждое состояние может изменяться независимо — изменение того, как выглядит или ведет себя `LoadingCurtain`, никогда не рискует задеть логику сохранения/прогресса, и наоборот.
* Каждое состояние можно тестировать или анализировать без необходимости понимать задачи другого.
* Порядок между ними явный, и его можно изменить или расширить (например, вставить получение удаленной конфигурации между ними) без реструктуризации самих состояний.

`HubState`

Завершающее цикл стейт-машины состояние в текущем виде проекта. В данном состоянии не выполняется никакой логики, оно нужно исключительно для того, чтобы завершить паттерн State-Machine.

#### 6.3 Почему все состояния реализуют `IState`?

Общая абстракция `IState` означает, что класс, управляющий переключениями состояниями стейт-машины должен знать только о `Enter()/Exit()` (или аналогичных членах жизненного цикла) — ему никогда не нужно знать, какое состояние выполняется в данный момент. Именно это позволяет добавлять новые состояния позже (например, `PauseState`, `RewardState`) без необходимости изменять сам драйвер конечного автомата.

### 7. MVP (Model-View-Presenter)

[_Вернуться к содержанию раздела Архитекутра_](#архитектура)

UI-архитектура следует паттерну MVP из семейства MV* — а именно варианту **Passive View** MVP, который обычно считается самой сильной и наиболее тестируемой формой MVP.

#### 7.1 Почему выбор пал на MVP, а не MVC или MVVM.

**Почему не MVC?**

В классическом MVC **View** может читать данные напрямую из **Model**, а роль **Controller** в основном сводится к трансляции ввода в обновления **Model** — сам **View** все еще несет некоторую ответственность за отрисовку на основе состояния **Model**, которое он наблюдает напрямую. В контексте Unity это имеет тенденцию размывать границу между "Unity-специфичным кодом рендеринга" и "логикой приложения", потому что **View** в итоге вынужден знать о структуре **Model** напрямую. MVP был выбран специально во избежание этого: здесь **View** намеренно пассивен и не имеет прямых отношений с **Model** вообще.

**Почему не MVVM?**

MVVM полагается на связующий слой (**ViewModel** предоставляет наблюдаемые свойства, к которым **View** автоматически привязывается) — это естественно подходит для фреймворков со встроенным data-binding, но в системе UI Unity (здесь используется uGUI) нет встроенного декларативного механизма привязки данных. Реализация MVVM в Unity должным образом означает создание кастомного связующего слоя с нуля, что является дополнительной инфраструктурой, не нужной в рамках этого проекта. MVP достигает того же разделения ответственности — UI-логика изолирована от рендеринга — через простые вызовы методов и C#-события, которые uGUI уже поддерживает изначально без дополнительных механизмов.

**Почему именно Passive View, а не классический MVP?**

В классическом MVP View все еще может содержать некоторую логику и может ограниченно взаимодействовать с Model. В Passive View View сводится к абсолютному минимуму: он предоставляет простые методы/свойства (например, "установить этот текст", "установить состояние интерактивности этой кнопки") и генерирует простые события ввода (например, "кнопка нажата") и не содержит никакой логики приложения. Все принятие решений — что показывать, когда и почему — полностью находится в Presenter.

#### 7.2 Маппинг паттерна в этом проекте:

* **Model** — данные: `PlayerProgress` (и его подобъекты, такие как `PlayerResources` и `PurchaseData`) и данные `TripleOfferEvent` (предложения, оставшееся время), в зависимости от того, с каким сервисом или доменным объектом работает конкретный Presenter.
* **View** — Unity-сторонние компоненты (отображение ресурсов в HUD, кнопка магазина с таймером обратного отсчета, сама панель магазина с тремя слотами предложений). Каждый View предоставляет только "глупые" сеттеры (обновить отображаемое количество, обновить текст таймера, включить/выключить кнопку магазина) и передает сырой ввод (нажатие кнопки) наверх — он не принимает решений о том, какими должны быть эти значения.
* **Presenter** — владеет фактической логикой: он читает данные из Model/сервисов (`PlayerProgress`, `TripleOfferEvent`, `IIAPService`), решает, что View должен сейчас отображать, и вызывает простые сеттеры View. Он также обрабатывает события ввода, которые генерирует View (например, "кнопка покупки нажата" - значит вызвать `IIAPService.MakePurchase`).

**Почему важно, чтобы Presenter ничего не знал о типах Unity UI, напрямую участвующих в рендеринге, а View ничего не знал о доменных типах Unity?**

Эта граница — то, что делает паттерн полезным практически. Поскольку Presenter вызывает только небольшой абстрактный интерфейс View (а не конкретные компоненты `Text`/`Image`/`Button`), логика принятия решений в Presenter — "должна ли кнопка покупки быть интерактивной", "какое значение показывать после изменения ресурса" — может быть выполнена и протестирована без создания каких-либо объектов UI. А поскольку View никогда не обращается к `PlayerProgress` или к каким-либо сервисам, визуальная реализация (как анимируется число, как выглядит состояние "куплено") может полностью измениться без какого-либо влияния на логику, которая решает, когда это состояние должно наступить, и это и есть главный плюс этого паттерна.

#### 7.3 Разбор конкретного примера

В магазине есть три предложения. Каждое предложение содержит тип ресурса (драгоценные камни, монеты, железо), количество и цену. Нажатие на кнопку магазина открывает магазин; нажатие на отдельное предложение покупает его, добавляет ресурс в ресурсы игрока и запускает сохранение. Когда все три предложения куплены, кнопка магазина становится визуально неактивной (затемненной).

Эта последняя деталь — затемнение кнопки магазина после покупки всех предложений — является хорошей иллюстрацией того, почему MVP и Observer (следующий подраздел) так хорошо сочетаются: Presenter кнопки не опрашивает каждые кадр "все ли предложения уже куплены?". Он реагирует на событие, которое генерируется ровно один раз, в момент покупки последнего предложения.

#### 7.4 MVP естественным образом порождает паттерн Observer

Поскольку **Presenter** подписывается на события изменений **Model** (события об изменении данных`PlayerProgress` и `TripleOfferEvent.OnAllOffersPurchased`), результирующее отношение является паттерном Observer. Когда `PlayerProgress` изменяется (например, обновляется количество ресурсов после покупки), генерируется событие; соответствующий Presenter, подписавшийся на него, получает уведомление и обновляет свой View необходимым образом. Это означает, что UI не нужно опрашивать или вручную обновлять извне — он реагирует автоматически и только когда что-то действительно изменилось, что одновременно эффективнее и устраняет целую категорию ошибок когдра разработчик забывает обновить элементы UI.

### 8. Save-Load система

[_Вернуться к содержанию раздела Архитекутра_](#архитектура)

#### 8.1 Выделенный сервис, вместо разбросанных по коду сохранений и загрузок.

Сохранение — это задача, которая нужна многим частям приложения (ресурсы игрока, история покупок и потенциально больше состояний позже), но ни один из этих клиентов не должен знать, как или где хранятся данные. Централизация этого в `SaveLoadService`, доступном через `ISaveLoadService`, означает, что каждый клиент просто запрашивает `PlayerProgress` и доверяет тому, что он корректно загружен/сохранен — путь к файлу, формат сериализации и стратегия записи полностью инкапсулированы внутри одного сервиса.

#### 8.2 JSON и Newtonsoft.Json.

JSON удобен тем, что он человекочитаем (полезно во время разработки для прямого просмотра/редактирования файлов сохранений) и естественно подходит для сериализации графа обычных C#-объектов данных, таких как `PlayerProgress`. 

**Newtonsoft.Json** был выбран вместо встроенной **JsonUtility** Unity, потому что у **JsonUtility** есть реальные ограничения, которые здесь имеют значение — он не поддерживает сериализацию `Dictionary<TKey,TValue>`, плохо работает с полиморфными типами и полями-интерфейсами, а также имеет ограниченную поддержку callback-ов сериализации. Newtonsoft.Json поддерживает все это надежно, включая те более богатые графы объектов (`PurchaseData`, `PlayerResources` как вложенные объекты с собственными событиями изменений), которые фактически есть в данных сохранения этого проекта.

#### 8.3 Сохранение/загрузка сделаны асинхронными, а для чего?

`SaveLoadService` **асинхронен, потому что операции ввода-вывода с файлами могут занимать реальное время, даже для небольшого файла**. Запись на диск не гарантирует мгновенности и может иногда подвисать, особенно на низкопроизводительных мобильных накопителях или при конкуренции за ввод-вывод. Выполнение `File.WriteAllTextAsync` (и чтения) асинхронно означает, что главный поток — а следовательно, цикл рендеринга/ввода — никогда не блокируется в ожидании доступа к диску. Это имеет большее значение, чем может показаться на первый взгляд, потому что сохранения в этом проекте происходят часто и автоматически, а не только в нескольких контролируемых точках — см. раздел 8.4 ниже. Блокирующее синхронное сохранение, срабатывающее при каждом изменении ресурса, создавало бы риск заметных микро-задержек; асинхронное — нет.

#### 8.4 Автосохранения через событиям.

`SaveLoadService` подписывается на `PlayerProgress.PurchaseData.OnPurchaseDataChanged` и `PlayerProgress.PlayerResources.OnPlayerResourcesDataChanged` и инициирует сохранение при срабатывании любого из них. Это решение лучше явного вызова `SaveProgress()` из каждого места в кодовой базе, по нескольким причинам:

* **Корректность по построению**. Если бы сохранение полагалось на то, что каждый объект будет помнить о необходимости вручную вызвать `SaveProgress()` после изменения, достаточно одного нового функционала (например, нового места, где выдаются ресурсы), забывшего вызвать сохранение, чтобы система сохранения бесшумно разъехалась с фактическим состоянием игры. Автосохранение на основе событий делает это невозможным по построению — любая мутация, генерирующая событие изменения, инициирует сохранение.
* **Правильное разделение ответственности**. Компонент, вызывающий изменение данных (например, `IAPService` после покупки), не должен знать или заботиться о том, должно ли после этого произойти сохранение — он просто передаёт данные и генерирует свое доменное событие ("данные покупок изменены"). Вызовет ли это сохранение или нет — это дело `SaveLoadService`, а не `IAPService`. Это не позволяет `IAPService` быть связанным с задачами сохранения, о которых он не должен знать.

Это то же отношение "Наблюдатель", обсуждавшееся в разделе MVP, примененное на уровне сохранения вместо UI-слоя — тот же базовый механизм естественным образом служит двум разным целям.


#### 8.5 Сервис `SaveLoadService` ничего не знает о UI.

`SaveLoadService` предоставляет данные и событие "прогресс загружен"; у него нет ссылок на какие-либо View, Presenter или UI-типы, и нет причин для этого. Это прямо следует из Dependency Inversion и описанных ранее границ сборок: сборка **Services** не может ссылаться на UI Logic, даже если бы кто-то этого захотел. Сохранение и UI представление данных сохранения — это разные задачи, которые меняются по разным причинам, и их связывание означало бы, что редизайн UI может сломать логику сохранения, или наоборот. Именно такое случайное связывание вся архитектура призвана предотвращать.

### 9. Static Data

[_Вернуться к содержанию раздела Архитекутра_](#архитектура)

#### 9.1 Статические данные отделены от рантайм-данных.

В этой системе существуют два действительно разных вида "Offer"-ов, и их смешение было бы ошибкой:

* `OfferConfig` / `TripleOfferConfig` — это статичные данные: какие предложения существуют, сколько они стоят, когда начинается и заканчивается событие. Это данные, которые редактирует геймдизайнер или разработичик.
* `Offer` — рантайм-модель, фактически используемая кодом геймплея/UI, которая включает вещи, которых нет в конфиге (например, загруженный **Sprite**) и представляет текущее состояние предложения в памяти, с которым может взаимодействовать игрок. **Для преобразования `OfferConfig` в `Offer` опередлён специальный сервис: `OfferDataService`** _[(подробнее в разделе 9.3)](#93-offerdataservice-осуществляет-маппинг-а-не-только-чтение)_.

Хранение этих двух типов отдельно, а не в одном общем классе, означает, что формат конфига может развиваться (добавить новое поле, реструктурировать JSON) без риска повлиять на то, как рантайм-код использует `Offer`, и наоборот — рантайм-специфичные вещи (например, ссылка на загруженный **Sprite**) никогда не должны загрязнять схему сериализуемого конфига.

#### 9.2  Почему именно JSON для конфигурации?

Конфигурация события — это данные для геймдизайнеров/разработчиков, которые выигрывают от того, что они **человекочитаемы и их легко редактировать или генерировать внешне** — включая, в реальном производственном контексте, генерацию на серверной стороне и отправку для обновления предложений, цен или времени живого события без обновления приложения. JSON естественно подходит для этого: его легко редактировать вручную, легко валидировать и легко парсить с помощью Newtonsoft.Json — что согласуется с выбором сериализации, уже сделанным для данных сохранения.

#### 9.3 `OfferDataService` осуществляет "маппинг", а не только чтение

Стоит точно определить, что на самом деле делает `OfferDataService`, потому что он делает больше, чем просто "загружает JSON". Он выполняет настоящее преобразование **DTO к Runtime Model**, то есть маппинг: `OfferConfig` (десериализованный DTO, почти прямое отражение структуры JSON) преобразуется в `Offer` (рантайм-модель), включая разрешение адреса изображения в фактически загруженный **Sprite** через `AddressableAssetProvider`. Этот шаг преобразования в точности паттерн Mapper — явный слой трансляции между внешним представлением данных и внутренней моделью, с которой фактически работает остальная часть приложения.

**Почему нужен маппинг, вместо того чтобы просто использовать объект конфига напрямую везде?**

Потому что это позволяет JSON-схеме и рантайм-модели Offer расходиться и развиваться независимо. Если формат JSON должен измениться (новые поля, реструктурированная вложенность, совершенно другой источник конфига), только шаг маппинга внутри `OfferDataService` должен измениться — каждый клиент, работающий с Offer ниже по потоку, остается полностью незатронутым, потому что они изначально никогда не зависели от структуры JSON.

#### 9.4 Два отдельных типа конфига — конфиг события и конфиг предложения.

`TripleOfferConfig` описывает само событие (время начала, время окончания, продолжительность), в то время как каждый `OfferConfig` внутри него описывает одно конкретное предложение (тип ресурса, количество, цена, адрес изображения). Это разделение отражает реальное концептуальное различие: "когда запущено это событие" — это свойство события в целом, а "что можно купить" — это свойство каждого отдельного предложения внутри него. Разделение означает, что время события можно корректировать без изменения определений предложений, а предложения можно добавлять, удалять или балансировать без изменения времени события — две независимые оси изменений, смоделированные как два независимых типа.

#### 9.5 Удобство масштабирования.

Поскольку новые типы событий могут вводить свои собственные пары конфиг/рантайм-модель и свои собственные сервисы-эквиваленты маппера, следуя той же форме, что установлена здесь, без необходимости модифицировать `OfferDataService` или `TripleOfferEvent` вообще. Вышеописанный паттерн устанавливается однажды и полностью лекго повторяем.

### 10. TripleOfferEvent

[_Вернуться к содержанию раздела Архитекутра_](#архитектура)

`TripleOfferEvent` - это фактическая имплементация события, обращенная к геймплею, и она наглядно демонстрирует, как несколько уже обсуждавшихся принципов работают вместе.

#### 10.1 Разделение отвественностей:

* `TripleOfferEvent` — управляет жизненным циклом события с точки зрения того, какие предложения доступны в данный момент: проверяет, активно ли событие (еще не началось, еще не закончилось), загружает/фильтрует предложения (удаляя уже купленные через `ISaveLoadService`) и предоставляет предложения любому Presenter, который их запрашивает. Он также реагирует на покупки (`IIAPService.OnOfferPurchased`), удаляя купленное предложение из активного списка и сигнализируя, когда все предложения куплены.
* `OfferDataService` — как описано выше, является слоем данных/конфигурации: он знает, как читать и маппить конфигурацию предложений/событий в рантайм-объекты `Offer`. `TripleOfferEvent` не знает и не заботится о том, как были получены эти данные — он просто запрашивает их.
* `TripleOfferEventTimer` — владеет только логикой времени: сколько времени осталось, сколько времени до начала события, а также генерацией событий `OnTimerTick`/`OnTimerEnd`.

#### 10.2 Логика времени вынесена в отдельный класс, а не находится внутри `TripleOfferEvent`.

Это применение SRP с высокой точностью: задача `TripleOfferEvent` — управлять тем, какие предложения действительны и доступны для покупки; он не должен также знать, как реализован обратный отсчет (цикл опроса с `UniTask.Delay`, `CancellationTokenSource` для корректной отмены и т.д.). Вынося это в `TripleOfferEventTimer` за интерфейс (`StartTimer()`, `StopTimer()`, `GetRemainingTime()`, плюс события `OnTimerTick`/`OnTimerEn`), `TripleOfferEvent` взаимодействует только с небольшим стабильным контрактом, и реализация того, как отслеживается время, может полностью измениться (например, переход от цикла опроса к сравнению временных меток, синхронизированных с сервером) без каких-либо изменений в `TripleOfferEvent`.

Это также дает конкретное преимущество в тестируемости, согласующееся с ранее обсуждавшимся DI: логику фильтрации предложений и проверки валидности `TripleOfferEvent` можно тестировать, внедряя фейковый `IEventTimer`, который возвращает контролируемые значения времени, без необходимости реального работающего таймера или реального системного времени во время теста.

#### 10.3 Как архитектурные решение переплетаются вместе.

`TripleOfferEvent` зависит от `IOfferDataService` (для получения данных предложений/конфига), `IEventTimer` (чтобы знать, активно ли событие и сколько времени осталось), `ISaveLoadService` (для фильтрации уже купленных предложений) и `IIAPService` (для реакции на уведомления о покупках) — каждый из них как интерфейс, внедряемый через конструктор, в точности согласно установленным ранее принципам DI. Каждое архитектурное работает вместе одновременно: DI для зависимостей, SRP для объяснения, почему каждая зависимость существует как отдельный класс, а не поглощена самим `TripleOfferEvent`, и Observer для того, как он одновременно реагирует на (`IIAPService.OnOfferPurchased`) и генерирует (`OnAllOffersPurchased`, `OnEventStarted`, `OnEventEnded`) события, на которые подписываются другие части системы.

### 11. Addressables

[_Вернуться к содержанию раздела Архитекутра_](#архитектура)

Проект использует систему Addressables для управления ресурсами, доступ к которой осуществляется через абстракцию — `IAddressableAssetProvider` вместо прямых вызовов Addressables API из случайных мест в коде.

#### 11.1 Почему выбраны Addressables?

Основная конкретная причина в этом проекте — **сами UI-префабы**: панель магазина, слоты предложений и связанные с ними элементы интерфейса загружаются как Addressable-ресурсы, а не как прямые сериализованные ссылки на сцены/префабы. Это было осознанным решением, потому что это означает, что визуальное представление UI может обновляться удаленно, независимо от остальной части приложения:

* Addressables отделяют адрес ресурса (строковый ключ, используемый в коде) от его физического расположения и хранилища (которое может быть локальной сборкой, удаленным CDN-хостом или вообще перераспределено в другой бандл) — без изменения ни одной строки кода, который его запрашивает.
* В контексте LiveOps это имеет конкретное значение: префаб UI, на который ссылаются по адресу, может быть заменен на обновленную версию, доставленную удаленно (новая компоновка магазина, переоформленный слот предложения, сезонное визуальное обновление) **без необходимости обновления в магазине приложений или пересборки билда**. Прямые ссылки на префабы или вызовы `Resources.Load` не предлагают аналогичного пути — оба требуют, чтобы ресурс был встроен непосредственно в сборку.
* Это также позволяет в принципе уменьшить начальный размер сборки/загрузки, поскольку не каждый ресурс должен быть упакован в базовую сборку — ресурсы могут быть загружены по требованию или доставлены удаленно, что становится важнее по мере роста контента проекта (больше событий, больше сезонных UI-вариантов и т.д.), чем в текущем объеме этого демо.

В этом примере Addressables используются конкретно для UI-префабов и изображений предложений (загружаемых `OfferDataService` через того же провайдера), но тот же механизм обобщается на любой тип ресурсов — те же обоснования (возможность удаленного обновления, отделение логической ссылки от физического хранилища) применимы независимо от того, является ли ресурс UI-префабом, спрайтом или, в более крупном проекте, аудио или данными уровней.

#### 11.2 Доступ к Addressables ресурсам осуществляется через сервис `IAddressableAssetProvider`.

Это следует той же логике Dependency Inversion, применяемой везде в проекте: никому за пределами этого провайдера не нужно знать, что именно Addressables является базовой системой управления ресурсами. `OfferDataService` вызывает `LoadAssetAsync<Sprite>(address)` и понятия не имеет, стоит ли за этим `Addressables`, `Resources` или какой-либо другой будущий конвейер ресурсов. Это означает:

* Специфичные для `Addressables` концепции (хендлы, управление жизненным циклом асинхронных операций, семантика освобождения) полностью инкапсулированы внутри одной реализации, вместо того чтобы просачиваться в каждого клиента, которому случайно понадобился ресурс.
* Если конвейер ресурсов когда-либо потребуется изменить — другое решение для бандлов, кастомный загрузчик через CDN — только реализация `IAddressableAssetProvider` должна будет измениться. Каждый клиент (`OfferDataService`, код загрузки UI, что угодно еще) продолжает вызывать тот же интерфейс, полностью не подозревая, что под ним что-то изменилось.

### 12. Асинхронное программирование

[_Вернуться к содержанию раздела Архитекутра_](#архитектура)

Как уже упоминалась ранее в других разделах - в проекте применяется асинхронное программирование. Здесь обсудим данную тему детальнее.

#### 12.1 Почему выбраны UniTask, а не .NET Task?

* **Отсутствие накладных расходов на пул потоков для однопоточной модели Unity**. Task был разработан для общего .NET, который является многопоточным. Unity же однопоточный (_если мы говорим о основном игровом цикле_), большинство асинхронных задач (ожидание кадра, ожидание хендла Addressables, короткая задержка) вообще не требуют потока из пула, а механизмы Task несут накладные расходы на выделение памяти, которые в этом контексте оказываются лишними. UniTask построен специально вокруг **PlayerLoop** **Unity**, поэтому стандартные операции (`UniTask.Delay`, `UniTask.Yield`, ожидание хендла `Addressables`) выполняются с гораздо меньшими накладными расходами на аллокации.
* **Нативная интеграция с жизненным циклом Unity**. UniTask предоставляет первоклассную поддержку для прямого ожидания нативных асинхронных операций Unity (хендлы Addressables, AsyncOperation) без необходимости написания оберточного кода для их преобразования в Task-совместимые ожидаемые объекты.
* **Отмена, соответствующая жизненному циклу объектов Unity**. UniTask корректно работает с `CancellationTokenSource`/`CancellationToken` в паттернах, которые естественным образом соответствуют времени жизни объектов Unity (например, корректная отмена цикла таймера через `Dispose()`, как показано в `TripleOfferEventTimer`).

#### 12.2 Почему не Coroutines?

Корутины (основанные на `IEnumerator`, запускаемые через `StartCoroutine`) не использовались, потому что у них есть реальные, хорошо известные ограничения, которые важны именно для этой кодовой базы:

* **Нет возвращаемых значений**. Корутина не может напрямую вернуть результат (например, "успешна ли покупка", "вот загруженный Sprite") — результаты приходится вытаскивать через колбэки или разделяемое изменяемое состояние, что является именно тем неявным, трудноотслеживаемым потоком данных, которого проектные принципы этого проекта стараются избегать везде.
* **Нет структурированного распространения исключений**. Исключения внутри корутины не распространяются на вызывающую сторону так, как это делает исключение в цепочке `async/await`, что делает обработку ошибок значительно более неудобной.
* **Привязанность к MonoBehaviour**. Корутины требуют живого `MonoBehaviour` для выполнения; обычные C#-классы сервисов (а это практически все, что находится в **Services**-слое этого проекта, намеренно, чтобы оставаться несвязанными с компонентной моделью Unity) не могут запустить корутину без неудобных обходных путей. UniTask, напротив, работает в любом обычном C#-классе.
* `async UniTask`-методы же в свою очередь возвращают значения, распространяют исключения через обычные `try`/`catch` и работают идентично как внутри обычного сервисного класса, так и внутри `MonoBehaviour` — **что является именно той унифицированностью, на которую полагается сервис-ориентированный дизайн этого проекта.**

#### 12.3 Асинхронность используется только там, где она действительно нужна.

Не все в проекте асинхронно — например, простые синхронные геттеры и чистые преобразования данных остаются синхронными. Асинхронность зарезервирована специально для операций, связанных с реальным ожиданием: файловый ввод-вывод (`SaveLoadService`), загрузка Addressable-ресурсов (`OfferDataService`, провайдер ресурсов), запланированные задержки (`TripleOfferEventTimer`) и интерфейс, намеренно сформированный для будущего ожидания (`IIAPService`). Бездумное использование `async/await` для операций, которые никогда ничего не ожидают, добавляет когнитивную нагрузку (каждый вызывающий теперь должен `await` или `.Forget()` что-то) без соответствующей выгоды, плюс к этому эту ещё нужно понимать, что ключевое слово `async` под капотом генерирует **State-Machine**, что влечёт к дополнительным аллокациям, вызовам **GC** и как следствие нагрузку на систему. По всем этим причинам асинхронность применяется только там, где это необходимо.

#### 12.4 Пример асинхронных сервисов: `IAPService` and `SaveLoadService`.

Как уже установлено в [разделе 8.3](#83-сохранениезагрузка-сделаны-асинхронными-а-для-чего): `SaveLoadService` **асинхронен из-за текущих затрат на файловый ввод-вывод** (реальные дисковые операции, которые могут заблокировать главный поток при синхронном выполнении и которые происходят здесь часто из-за событийно-управляемого автосохранения). 

`IAPService` **асинхронен из-за предполагаемой будущей необходимости** (реальный процесс покупки будет включать сетевые вызовы к магазину/бэкенду, которых пока нет в заглушке этого примера).

### 13. Расширяемость

[_Вернуться к содержанию раздела Архитекутра_](#архитектура)

Этот финальный раздел является, по сути, практическим результатом всех решений, описанных выше: поскольку система построена на интерфейсах, внедрении зависимостей и четком разделении ответственностей, несколько категорий будущих изменений могут быть выполнены **без модификации существующего рабочего кода — что является принципом Open/Closed**. **Примеры:**

* **Замена** `IAPService`. Текущая реализация намеренно является простой заглушкой. Поскольку каждый клиент зависит от `IIAPService`, а не от `IAPService`, внедрение реальной реализации с покупками через магазин платформы/бэкенд-валидацией позже — это вопрос написания нового класса и изменения одной привязки в Zenject-инсталлере — `TripleOfferEvent`, любой Presenter и все остальное, что использует `IIAPService`, не требует никаких изменений.
* **Замена бэкенда сохранения**. Замена локального JSON-хранилища на, скажем, облачные сохранения или другой формат сериализации полностью инкапсулирована за `ISaveLoadService`. Каждый клиент запрашивает `PlayerProgress` одним и тем же способом, независимо от того, где и как фактически хранятся данные под капотом.
* **Добавление нового события**. Триада `TripleOfferEvent` / `OfferDataService` / `TripleOfferEventTimer` задает повторяемую форму (конфиг - маппер - рантайм-модель, плюс изолированный таймер), которой может работать с новым типом события независимо, без необходимости изменять классы существующего события.
* **Добавление новых предложений**. Поскольку предложения полностью управляются конфигом (JSON, маппинг в рантайм-модель `Offer`), добавление, удаление или балансировка предложений — это чистое изменение контента/данных, не требующее изменений в коде вообще.
* **Добавление нового механизма хранения в более общем смысле**. Поскольку сохранение полностью инкапсулировано за `ISaveLoadService`, а загрузка ресурсов полностью инкапсулирована за `IAddressableAssetProvider`, внедрение совершенно нового механизма хранения или доставки для любого из них — это вопрос написания новой реализации за существующим интерфейсом.
* **Замена Addressables**. Поскольку ничто за пределами `IAddressableAssetProvider` не вызывает Addressables API напрямую, весь конвейер ресурсов в принципе может быть заменен на другую систему без изменения `OfferDataService`, кода загрузки UI или чего-либо еще, что сейчас просто вызывает `LoadAssetAsync<T>(address)`.

Таким образом данный MVP проект легко масштабировать, так как он представляет собой крепкий фундамент.**Каждая точка вероятного будущего изменения в этом проекте находится за интерфейсной границей, которая была установлена намеренно и заранее**, с планированием на будущее расширение. В этом и заключалсь первоочередная цель проекта - продемонстрировать качественные подход к разработке и архитектуру.
